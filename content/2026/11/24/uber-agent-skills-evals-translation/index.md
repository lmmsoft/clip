## 企业级规模下的技能（Skills at Enterprise Scale）

技能（skill）是一个 Markdown 文件，它教会 AI 智能体把一件事做好，例如创建 pull request、查询指标库，或起草每周销售演示。技能是 [Uber 软件工厂](https://www.uber.com/us/en/blog/efficient-software-factory/)的构件之一。Uber 的共享技能市场在一年内从 2025 年 10 月的 1 个技能增长到超过 5,000 个。数千人编写过技能，智能体在短短一个月内调用技能超过 100 万次。

在企业级规模上，技能的管理、质量、效率和分发带来了许多挑战与机遇。本文写给正在全公司范围内推广智能体的团队：我们分享如何改进 AI 赋能，以及如何借助智能体来提供帮助。

### 什么是技能（What Is a Skill）

技能是一个工作流，而「企业的最小单元就是工作流」。[1]

一项技能封装一个工作流：一份运行手册（runbook）、一个团队的流程，或某位专家手工完成的任务。它可以是修改一个 Linear® 工单这么短，也可以是完整的根因分析这么长。

在磁盘上，技能是一个目录。它的 SKILL.md 文件包含名称、描述和指令正文。目录还可以存放脚本和参考文件。智能体分三个阶段加载它，因此数千个技能只消耗一段简短的描述：

- **始终加载**：名称和描述，约 100 个 token。智能体用描述判断该技能是否适用。
- **技能运行时加载**：正文，保持在 500 行以内。
- **按需加载**：脚本和参考文件，只由需要它们的步骤读取。

![图 1：技能目录的结构，以及智能体在何时加载其中每一部分](https://tb-static.uber.com/prod/udam-assets/89c986e4-39b8-4614-9264-8286ff3c016c.png)

[Agent Skills 规范](https://agentskills.io/)详细描述了这一开放格式。

### 分发技能（Distributing Skills）

我们创建了一个统一存放技能的地方，让技能在人们使用智能体的任何地方都能轻松加载。事实证明，最好的载体是 Git® 仓库，因为版本控制天然为每个技能提供了负责人、评审和历史。

### 治理之道：Always-On、Core 与 Domain（Organizing the Madness）

我们的目标是让团队容易编写技能，同时默认提供一套经过筛选的技能。为了实现快速但高质量的开发，我们把市场分成三层，技能每往上「毕业」一层，对质量和效率的期望就提高一分。技能要毕业，需要通过我们的评估系统以及一组质量与有用性检查。

- **Domain（领域层）**：任何团队都可以开辟自己的领域。每个领域自行指定评审人，因此团队只需一位同事批准加一次 CI 检查即可发布，不必等中央团队。
- **Core（核心层）**：被广泛使用的技能移到这里。它们由专门团队推荐、测试和维护，平台团队评审每一次变更。
- **Always-on（常开层）**：约 100 个广泛有用的技能对所有人默认开启，新员工第一次运行就有技能可用。它们覆盖 pull request、代码评审、工具访问、数据分析和聊天。

![图 4：三层结构、一个插件（plugin）包含的内容，以及从 pull request 到发布的路径](https://tb-static.uber.com/prod/udam-assets/4932563b-842e-428b-9e0d-f1d77aa37814.png)

### 一次安装，适配所有智能体（One Install for Every Agent）

支持多种不同的智能体是我们战略的一部分。它是机遇，因为人们可以按任务挑选合适的智能体；它也是挑战，因为每个智能体定义和安装技能的方式各不相同。

我们做了命令行工具 **aifx**，用于启动各类智能体和保存配置，后来又扩展出技能管理、MCP 调用、可观测性和更高级的配置。aifx 处理各平台在技能定义和安装上的差异。一个人或一个智能体运行 `aifx plugin add data-analyst` 安装一组技能（称为[插件（plugin）](https://code.claude.com/docs/en/plugins)），或运行 `aifx skill add analyze` 安装单个技能。aifx 把选择记录在一个配置文件里，并应用到下一个启动的智能体。在 Claude Code™、Codex™ 和 OpenCode™ 之间切换的工程师，拿到的技能是同一套。

![图 5：aifx 的作用——一个命令行工具，让每个智能体获得相同的登录、技能和工具](https://tb-static.uber.com/prod/udam-assets/786b980d-751a-48eb-ad1b-eadb6fce8e0c.png)

aifx 按层合并配置：公司默认、团队或项目、仓库、工作目录、用户，以及本地覆盖。后面的层只追加插件，从不移除，因此一个仓库可以声明所有在其中工作的人都需要的插件。aifx 还为工程师、数据科学家和其他角色管理 persona，设定各自的默认技能和配置。

![图 6：aifx 合并六层配置，并把结果写入每个智能体自己的配置](https://tb-static.uber.com/prod/udam-assets/dbdbfd97-5b89-4065-96a8-bf2f1fe1a3dd.png)

![图 7：一个技能仓库同时供给笔记本上的智能体、托管智能体和搜索；遥测、评估与 papercut 回流给技能的负责人](https://tb-static.uber.com/prod/udam-assets/b5255b08-a424-4553-800b-071101c80c65.png)

### 技能发现（Skill Discovery）

在有数千个技能之后，帮助用户为某个工作流找到正确的技能变得至关重要。我们有一个 `find-skills` 技能，可以在具体工作流中找到并下载高质量的技能并运行它。为支持发现，我们用评估结果和运行次数对技能分类排序，并生成技能质量分。借助内部上下文图，任何员工都可以问：「给我看看我的同事在用、而我还没用的技能。」

![图 8：find-skills 技能如何为一条 prompt 找到技能](https://tb-static.uber.com/prod/udam-assets/2d672d66-dc60-4a21-8076-66bb18750f1e.png)

## 度量技能的使用（Measuring Skill Usage）

我们通过 hooks 中的 OpenTelemetry 从智能体收集使用统计。hooks 发送会话开始、工具调用等事件，让我们记录技能的使用及其上下文。当工具是技能时，事件记录该技能、它的版本，以及是智能体自行选择了它还是用户输入了它的命令。事件不包含 prompt 文本，也不包含文件内容。

![图 9：使用事件从智能体的 hook 到展示技能使用的页面的路径](https://tb-static.uber.com/prod/udam-assets/c5aee2e0-80a5-4969-acbd-7efcfcde17d6.png)

基于这些事件，我们为每个技能计算 12 项指标，包括用户数、留存、成本、延迟和错误。作者可以在 Skill Workshop（我们的创作工具）的技能页面上看到它们。

![图 10：我们为每个技能度量什么，以及每项指标的用途](https://tb-static.uber.com/prod/udam-assets/1cfdcad7-5217-45d1-98c1-518392d783be.png)

## 永无止境的技能质量之战（The Never-Ending Battle for Skill Quality）

技能构造的智能体工作流，带来的挑战与智能体本身不同：它们被期望在多种上下文中工作，在「正确答案需要人类判断」的领域中工作，以及在很多不同的智能体环境中工作。我们创建了 Skill Workshop——一个插件加一个 Web 应用——通过科学方法、系统化评估和用户反馈，帮助技能的作者和用户改进技能。

### Skill Workshop

技能有生命周期：作者编写它、测试它，通过市场发布；然后作者根据真实运行的表现改进它，直到更好的模型让它变得多余而退役。Skill Workshop 为每个阶段提供工作流，并为每个技能提供一页，展示它的使用、成本和质量。

技能从一份定义清晰的 spec 开始。模型和 harness 变化很快，我们希望技能在我们迭代实现的过程中保持可用。spec 保留技能的意图：它的目标、它的输出、必需或禁止的工具动作，以及它面向的智能体和模型。Skill Workshop 从 spec 编译出 SKILL.md 及其测试 prompt，并在模型或智能体变化时重新编译。

![图 11：Skill Workshop 中一个技能的页面及其三组工作流](https://tb-static.uber.com/prod/udam-assets/6b3dd082-4f93-4638-94ac-b079654061bd.png)

### 把技能代码异味提炼成 Linter（Skill Code Smell Distilled Into a Linter）

我们把「什么造就了好技能」「什么造成了问题」、研究论文和模型提示指南，提炼成一个带通过/不通过检查的 linter。以下是最有用的几条：

- 步骤编号，每步只有一个目标，并至少有一种（哪怕是软性的）验证方式。
- 每步给出具体命令，并在进入下一步之前检查其结果。
- 技能有错误恢复章节：一张失败与修复对照表。「再试一次」不算数。

### 评估（Evals）

仅靠用户手工反馈来判断技能质量远远不够。我们在多个智能体界面上建立了多套评估系统，创建了人工标注的 prompt 和运行时环境来测试它们。我们对评估套件的经验配比是：约 **5%** 的 golden cases——固定输入、带工具 mock 的期望输出；**80%** 的真实 prompt，按轨迹（trajectory）评分；**15%** 由作者判断。**轨迹**指智能体是否按正确的顺序使用了正确的技能和工具。

![图 12：一个评估套件中的 prompt 构成，以及我们测试技能变更的三种环境](https://tb-static.uber.com/prod/udam-assets/afeb8adb-1e5f-4a49-a43e-489266dbd11a.png)

评估在三个地方运行：后台智能体平台 **Minion**、托管智能体沙箱 **AES**，以及远程开发机 **devpods**。干净环境能暴露对作者本机的依赖。就像每个说「在我机器上是好的」的开发者一样，强制远程运行发现了很多问题：有些技能依赖特定的文件路径、缓存的文档，或特定的 OS 工具。

面对非确定性的 LLM，评估仍是半艺术半科学。我们的经验是：**通过率在 70%–90% 的评估，往往比 100% 通过的更有用**。答案本就会变化，裁判也会变化；100% 的通过率可能意味着评估遗漏了答案中有意义的变化。

判断一次评估运行是否通过，本质上是判断什么才重要：措辞需要完全一致吗？哪些变化不改变含义？智能体自己未必能稳定地做出这些区分——它们可能纠结无关细节，或在答案格式符合预期时漏掉一个严重的幻觉。LLM-as-judge 在有人工标注集时效果最好。技能作者必须创建这些标注集、从用户那里收集，并反复评分。这就是我们把评估套件拆分为 golden 集、真实 prompt 和作者自建用例的原因。

轨迹评估看智能体尝试做什么、为什么。它不看结果。智能体是否按预期使用了 MCP 或流程？是否查询了那张表、读了那份 Google Doc、检查了上下文图？是否查看了自己的错误恢复指令？我们用结果分和轨迹分一起来评估技能与工作流的变更。

### 少即是多：消融测试（Less Is Sometimes More: Ablation）

我们在隔离的评估环境中，用相同的输入 prompt 测试从工作流中移除一些文字甚至整个技能的效果。对整个技能，我们把真实 prompt 分别在带技能和不带技能时各重放一次，由盲评裁判选出更好的答案。我们用真实 prompt 测试了使用量最大的技能，比较带技能、不带技能以及只用技能的一部分；随着模型越来越好，更多的文字反而可能降低表现，所以我们也测试从技能中删掉一些文字。

![图 13：带技能产出的答案在盲评对比中的获胜比例，含 95% 区间；阴影带是每个技能的噪声带，即两次相同运行之间的差异](https://tb-static.uber.com/prod/udam-assets/a3534e1f-9372-4325-b3a6-f618e6202fb3.gif)

在大多数情况下，技能让会话更成功、成本更低。最大的收益来自那些给智能体提供了它本来难以找到或难以理解的东西的技能，例如内部文档的访问方式，或运行数仓查询的方法。

## 技能的效率（Skill Efficiency）

有了技能，我们就能度量一个任务的成本，因此我们把更多会话迁移到使用技能。不使用技能的会话可能会尝试很多东西、找到错误的答案和错误的表、把工具用得一团糟；使用技能后，得到正确答案的概率和效率都会上升。在我们对一个数仓查询技能的消融测试中：不使用技能的会话多出 **13%** 的工具调用，工具错误多 **6 倍**，耗时多 **31%**，而带技能的答案在 **87%** 的对比中胜出。

一个能改善答案的技能自身也有成本。它的指令、它的工具调用及其结果进入智能体的上下文，会话中之后的每一轮都要为这份上下文再次付费。我们度量每个技能的成本，并用几个杠杆来降低它。

### 我们如何度量一个技能的成本（How We Measure the Cost of a Skill）

智能体会持续累计会话至今的花费，我们的遥测以周期性快照上报这个总额。当智能体调用一个技能时，我们取调用前最后一次上报的总额和调用后第一次上报的总额，两者相减。差值就是那次调用的成本。我们把每个技能每天的调用成本加总，再除以调用次数，得到该技能的**每次调用成本**。

这个数字包含模型读取技能、随后的轮次，以及该时间窗内的任何其他工具调用。我们用它来看成本的去向，并在技能变更前后做比较。

### 我们用过的降本杠杆（The Levers We've Used to Reduce the Cost of a Skill）

一个中央团队追踪所有使用最广泛的技能的效率，平台负责人像对待 UI 或软件所有权那样对待技能所有权，为质量和效率设定 KPI。

- **用代码代替 LLM。** 永远不变的步骤在脚本中运行，模型不必读取每个工具定义和每条结果。这就是下文介绍的 Code Mode。
- **在更便宜模型的 worker 中运行技能。** 技能派发一个子智能体，由调用方选择模型：查询用小模型，关联结果用最强模型。大的工具结果留在 worker 的上下文里，只返回有界的摘要，后续轮次不必再为它付费。在前后对比中，一个追踪（tracing）技能的每次调用成本下降了 **46%**。一个部署技能在第一周没有表现出下降，所以我们对每个技能的每次变更都单独测量。
- **在技能加载时运行脚本。** 当结果很小且总是需要时，技能在加载阶段运行脚本并把输出放进 prompt，省掉一轮模型调用。一个搜索技能从 4 轮降到 3 轮，平均成本下降了 **32%**。
- **把轮询移出主会话。** 在我们支出最高的 20 个会话中，通知类轮次约占支出的三分之一。9 月，我们把 PR 监控技能的轮询移到了更便宜模型上的后台智能体。

### Code Mode：能用代码时就别用 LLM

对确定性工作而言，代码比 LLM 更便宜、更容易测试、结果更好。我们发现大量 token 花在重复的工具调用上：执行一次查询并读取响应、读取并发送一条 Slack® 消息、搜索远程代码、读取并发送邮件。智能体想要的只是结果，却必须让所有内容经过 LLM 和它的上下文窗口，这既慢又贵。

LLM 客户端里默认的 MCP 安装让情况更糟：每次调用都会把所有工具的完整描述加载进来。工具超过 100 个时，在用户输入任何内容之前，这些定义就要占掉 **5 万到 7 万个 token**。

受 [Cloudflare 的 Code Mode](https://blog.cloudflare.com/code-mode/) 启发，我们把这些流程迁移为通过我们的网关调用工具的工具脚本。在我们的配置下，这避免了预载那些工具定义，智能体只读取每条结果中它需要的部分。这些脚本改善了我们最常用流程的成功率、延迟和成本。

这些 code mode 技能变成了包，公司其他技能按名称引用它们，从而让各自的流程依赖高质量实现。我们还在技能和插件中封禁了 `.mcp.json` 文件——那会安装工具服务器。

## 持续改进与智能体自提 Bug（Continuous Improvement and Agents Filing Their Own Bugs）

一个技能会因为一千种原因停止工作：模型升级改变了智能体阅读指令的方式，工具改了参数，或智能体 harness 改变了技能的运行方式。

智能体自己知道技能、工具或流程什么时候不正常。当智能体挣扎着完成被交代的事、花了 100 轮和某个诡异错误缠斗时，它是有感知的。它看得到帮助文本里列出、却被工具拒绝的参数；看得到出错时却返回退出码 0 的命令；也看得到本应有匹配结果却返回空的查询。

智能体有时能找到绕行办法，但那会浪费大量 token 和宝贵的上下文。我们发现，增加一个随时可用的技能，让智能体把它感受到的摩擦或 bug 记录下来，能形成一个强大的改进飞轮。

### 问题发现（Problem Discovery）

我们把每份报告称为一个 **papercut**（纸割伤，意指小而磨人的问题）。智能体通过常开技能 `log-papercut` 提交它，因此每个智能体都看得到这个技能，无需被要求就能提交报告。这不仅改善未来的会话，也改善发生 bug 的那次会话：智能体知道有些东西可能出问题了，应该识别出自己正在挣扎，它甚至可以查别人是怎么绕过这个问题的。

报告写明智能体尝试了什么、期望什么、实际发生了什么、怎样能修好它。所有报告进入一个按技能分组的统一看板。

![图 15：一个智能体在 10 月提交的 papercut（有删节）。这些字段让我们能归并同类报告，也让报告能告诉负责人该修什么](https://tb-static.uber.com/prod/udam-assets/b44b7f6b-bb13-4c05-95e0-47c63948f8e7.png)

### 问题解决（Problem Resolution）

一个 papercut 要经历归并、分诊、根因分析、修复、评估和批准。修复上线后，还要被度量和检查回归，然后工单才会关闭。

![图 16：papercut 闭环。在两个标注的步骤上需要人参与](https://tb-static.uber.com/prod/udam-assets/37d243db-8241-41ae-addc-964e4777d7cf.gif)

短短三个月内，智能体提交了数千份 papercut，数百份已修复。这些修复既改善了工作流，也让它们节省了大量 token。以下是几个有意思的修复：

- PR 技能把 commit message 写进一个共享的临时文件，导致两个并发会话互相改写了对方的 pull request。
- 一个部署技能让智能体传 epoch 秒，而 API 期望的是毫秒。
- 一个配置查询技能在请求的 key 不存在时，不报错地返回了另一个属性。
- 一个 PR 技能在一个没有 CI 检查的仓库上等待 CI 结果，反复收到同一个 404，直到超时。

### 人的信号（Human Signals）

独立于智能体的自我判断之外，我们有人工评分员在评分智能体会话。在 Fawkes——Uber 的自动软件维护工厂——里，代码维护技能会创建 pull request。如果一个 PR 收到评论、被反复迭代，或未被合并，我们就用这些信号来改进生成它的技能。被卡住的 PR 会成为评估集的一部分。我们在许多领域和智能体平台上复用这一模式。

## 结论（Conclusion）

技能把文字变成了动作和结果。随着使用量增长和模型进步，我们的重点从「编写技能」转向「技能的质量与评估」。尚未解决的问题是：如何评估那些很少运行、却事关重大、又难以判断好坏的工作流。在投入这项工作时，我们正在试验轨迹与 trace 分析、结构化的人工标注，以及技能路由。

## 太长不看版（TL;DR）

- **所有智能体共用一种格式、一个仓库。** 同一个技能可以在笔记本上的 Claude Code™、OpenAI Codex™、OpenCode™ 和 Cursor® 中运行，也可以在所有托管智能体中运行。我们的命令行工具 aifx 为每个智能体界面提供身份认证、技能分发和 MCP 连接。
- **技能属于所有人，不只是工程师。** 工程师用它做根因分析、实验解读等几乎所有事；其他团队用它取指标、起草待评审文档，以及帮助客户经理回答商家支持问题。
- **先写 spec。** `spec.md` 记录技能必须产出什么、支持哪些智能体和模型。Skill Workshop（我们的创作工具）从它编译出 SKILL.md 和测试 prompt，使技能在模型和智能体变化时依然可用。
- **少有时胜过多。** 我们用真实 prompt 重放带技能与不带技能的情况，由盲评裁判选出更好的答案。随着模型变好，一些技能需要修改甚至退役。
- **从 trace 改进技能。** 作者在自己会话的 trace 中查看技能的失败点，把每次失败转化为一个测试用例。
- **智能体自己提 bug。** 当智能体遇到坏掉的参数、错误的文档或静默的错误时，它会提交一份名为 papercut 的结构化报告，由负责人接手。

## 接下来做什么？（What's Next?）

我们正在做以下工作：

- **技能 A/B 测试。** 我们想对技能内容做 A/B 测试，以在更大规模上评估它们。这将让我们对重要技能做金丝雀变更。
- **按模型编译技能。** 随着模型在提示指南和建议上发生漂移，我们发现不同措辞和长度的 SKILL.md 文件在不同模型家族上表现不同。
- **收集并处理技能运行的 trace。** 我们将按评估对会话建立索引，记录用户想做什么、发生了什么、是否遇到麻烦、是否成功。我们会追问：我们可以怎么改进？哪些东西效果好到应该分享给更多会话？
- **技能推荐。** 我们将告诉用户应该使用哪些技能。
- **一个任务路由器。** 对用户想做的每件事，他们只需问一个入口，由它路由到正确的智能体、技能和上下文。
