## 与 AI 研发效能的相关性

**高度相关。** 本文给出一个可直接套用的分析框架：把智能体总开支拆成「用户数 × 人均请求 × 每请求输入 token × 每请求输出 token × 每 token 价格」，逐项度量、逐项优化。Uber 在使用量扩大 7 倍的同时压低了所有单位成本指标。另有[中文译述版](/2026/11/24/uber-efficient-software-factory/index.html)可对照阅读。

## 引言

在 Uber，AI 工具已经嵌入软件开发的每一个阶段。超过 **70% 的 pull request** 由本地或云端智能体完成。工程师在整个软件开发生命周期内构建了 **3,600 多个智能体技能（agent skill）**，每天执行超过 **3 万次**技能调用。

在 AI Engineer 2026 大会上，我们分享了[软件工厂（Software Factory）的愿景](https://www.uber.com/blog/ai-engineer-2026-software-factory/)，以及我们围绕整个生命周期构建的构件和托管智能体。随着这一愿景的推进，越来越多的会话不再由人发起，而是由自动化的托管智能体处理：代码审查、CI 失败自愈、带视觉验证的端到端（E2E）PR、值班告警分诊、新进缺陷调试，以及在人工评审/升级介入下处理各类代码维护任务。

如图 1 所示，2026 年 2 月至 8 月，全体员工（工程师与非工程师）使用所有智能体产品的周活跃用户增长了 **7 倍**，每周智能体请求量增长了 **9.4 倍**。与此同时，得益于全方位的优化，我们的 AI 总支出自 4 月以来已相对稳定。

![图 1：2026 年 2 月至 8 月中的周活跃用户、智能体请求量与成本（用户跨工具去重）](https://tb-static.uber.com/prod/udam-assets/dda106d3-0439-427b-b780-c399dc85c7c8.png)

由于采用程度、工作负载结构和模型升级都在持续变化，要单独看出自身优化的效果，就必须固定一个模型来观察，因为模型家族每次升级都会改变行为。我们在 2 月至 7 月固定模型做了对比：每千次模型请求的成本较峰值下降近 **34%**，每次会话成本较 6 月峰值下降 **52%**。

![图 2：固定模型下的成本优化效果；*每次会话成本数据自 5 月底开始](https://tb-static.uber.com/prod/udam-assets/b25d175f-821b-4ba6-a149-14e5c95a25cb.png)

本文将介绍我们如何看待软件工厂：智能体会话运行的四个层次、我们用来拆解支出的成本公式、每一项如何度量，以及如何在每一层优化这些项。

文中所有价格与供应商指标均基于公开信息，成本效率的提升来自在标准分层定价内更智能地路由 Uber 内部工作负载。我们所测得的成本降幅是 Uber 环境特有的，你的实际效果会因代码库、团队规模和智能体工作流而异；但「用真实工作做基准、同时优化准确率与成本」的方法论是普遍适用的。

### 成本公式

在上述任何一层，我们都可以把一次智能体会话的成本分解为下面几项，并对它们分别度量和优化。

![图 4：总支出，分解为六个相乘的项](https://tb-static.uber.com/prod/udam-assets/caf91e7d-085d-4014-918f-afef7f7b299b.png)

前两项代表采用与参与度——无论用户是交互式使用，还是智能体代为处理任务，我们都希望它们在整个用户群中持续增长。中间三项提供了优化空间：智能体在工程师实际请求之外、为自己完成的工作。这正是我们大部分精力的投向，包括帮助智能体更快规划、减少多余轮次或错误、优化输入 token 等机制。

## 我们如何度量

下面是我们按周和按月追踪的全部指标，它们让我们能够进行短期和长期的预测与规划：

| 层次 | 指标 | 回答什么问题 |
| --- | --- | --- |
| 组合（Portfolio） | 归属总成本；归属的独立用户数；各工具/智能体的成本、用户数与支出占比 | 钱花在哪里，哪个工具带来了变化 |
| 单工具单位经济性 | 每用户成本；每用户请求数；每千次请求成本；每请求的输入、输出与总 token 数；每百万 token 成本；每千次会话成本；每活跃会话小时成本；prompt cache 命中率 | 工具是真的变便宜了，还是只是用量发生了转移 |
| 模型经济性 | 对每个模型：成本与成本占比；请求与请求占比；每千次请求成本；每百万 token 成本 | 哪些模型发布真正改变了账单——在相同或不同的每 token 价格下 |
| 驱动因素分解 | 把成本变化依次分解为：采用（用户数）；参与（每用户请求数）；输入负载（每请求输入 token）；输出负载（每请求输出 token） | 数字为什么变——精确表述，不留下任何无法解释的残差 |
| 托管智能体产出 | 对每个托管智能体：按产出计价的成本（每个已合并 PR 的成本、每次审查的成本、每条告警的成本、每次清理的成本）；质量信号（回滚率、F1、MTTR）；处理量（落地的 diff、发出的审查、分诊的告警） | 每个托管智能体每单位交付价值是否在变便宜，模型迁移过程中质量是否守住 |

## 优化价格 / Token

token 的单价由供应商决定，而由哪个模型来跑哪类工作负载由我们决定。在所有托管智能体的各个层次，我们都会为该工作负载挑选帕累托效率最高的模型。对我们而言，帕累托有效意味着：每个已完成任务的成本、输出质量与模型可靠性三者的综合最优。

### 基准驱动的模型选择

模型选择分四步进行，对我们运行的每个托管智能体都一样：

1. 用该智能体的真实工作构建基准。
2. 在统一接口后面可服务任意模型（前沿模型或开放权重模型）的 harness 上运行该智能体。
3. 迁移到帕累托最优的模型，并持续跟进——帕累托前沿每隔几周就会移动一次。
4. 展望未来，我们持续利用各托管智能体汇聚的洞察来测试并部署各种模型路由策略，不断改进工作负载表现。

以 **uReview** 为例，它为所有 pull request 提供 AI 代码审查。我们用带有已知缺陷的真实 PR 构建了它的基准，并按容易、中等、困难分级；对照这些缺陷计算精确率、召回率和 F1，同时衡量每次审查成本、延迟、超时和噪声。如图 5 所示，更换模型在提升 F1 的同时大幅降低了每个 PR 的成本。图中虚线为帕累托前沿，其左下方的一切配置都会被更便宜或更好的方案击败。

![图 5：我们为 uReview 测试过的每一个配置](https://tb-static.uber.com/prod/udam-assets/a3b68d79-4d1f-47d5-9524-5c0c404bdbd2.png)

我们还在内部用大型单仓库中的数千个真实 PR 构建了 **Uber SWE Benchmark**，让前沿模型和开放权重模型在不同任务类型上运行，用它的结果指导所有 SDLC 托管智能体的模型选择。

### 默认模型选择

在交互式界面中，token 单价保持不变，但你可以有策略地管理 token 在不同模型之间的分配。主要由两个默认设置决定这种分配：会话的初始模型和子智能体模型。

实践证明，**子智能体默认设置**是影响最大的杠杆，而且其重要性还在持续上升。随着最新模型能力使多智能体编排更加有效，发起子智能体的会话比例稳步上升。子智能体执行的是输入明确、定义清晰的任务，通常不需要前沿级的推理能力，因此我们默认让它们使用更弱、性价比更高的模型，同时保留手动覆盖的选项。主模型负责任务拆解与评估，子智能体负责执行工作。

## 优化 Tokens / 请求

每一轮都会重新发送完整的对话历史、项目上下文和工具结果。任何能减少单次请求负载的做法，都会在整个会话中被复合放大。

### 默认配置

所有交互式 harness 都使用统一封装来管理安装、配置、认证和成本可见性。两项标准化的默认配置直接降低了每请求的 token 消耗：

- **即使模型支持 100 万 token 上下文窗口，也会在 40 万 token 时触发自动压缩**。这一阈值在模型表现、缓存突发和重复输入成本之间取得平衡。我们的测量显示，全舰队每请求输入 token 出现了显著下降。
- **推理强度默认设为 Medium**。在主力模型上，输出 token（包括内部推理 token）的计费是输入 token 费率的数倍；这项策略调整直接压低了成本最高的 token 类别的支出。对很大一类任务而言，Medium 推理在成本与质量之间达到了良好的平衡。

### Prompt Caching 策略

我们的 prompt 缓存策略由供应商缓存读写的经济学驱动。由于每一轮都会重传完整的对话历史，缓存前文可以避免反复支付全价，把后续读取降到标准输入 token 费率的 **0.1 倍**。但写入溢价各不相同：**5 分钟**缓存条目的成本是 **1.25 倍**，**1 小时**条目是 **2 倍**。因此，选择最优 TTL（生存时间）取决于轮次之间间隔的时长。可选 TTL 包括 Anthropic® 的 5 分钟和 1 小时，以及 OpenAI® 的 30 分钟。

![图 6：两种 TTL 时长下 5 轮对话的成本对比](https://tb-static.uber.com/prod/udam-assets/f6134160-6beb-4272-8d88-2bee792d0403.png)

由于工程师经常让交互式会话空闲超过 5 分钟，我们把默认的 5 分钟 TTL 换成了 **1 小时窗口**。此前这些频繁的空闲间隔会使前缀缓存失效，迫使系统付出高昂代价、以全价重建上下文。相比之下，子智能体保留 5 分钟缓存 TTL，因为它们的执行焦点仅限于单个、短命的任务。

### 通过 Shell 执行 MCP 工具

在 Uber，所有 MCP（Model Context Protocol）交互都经由统一网关路由。这个唯一入口涵盖内部和第三方 SaaS MCP 的 **1,000 多个 MCP 服务器**，实现集中认证与策略执行。

然而，标准 MCP 会把所有工具 schema 直接加载进每个会话，无论工程师在该会话中是否会调用它们。例如，安装了 100 多个工具时，这种预加载会给初始 prompt 增加约 **5 万至 7 万 token** 的 schema 开销，并且在此后每一轮上下文中都会被重发。

![图 7：在 3 种接入同样工具的方式下，会话开始时智能体已经背负的内容](https://tb-static.uber.com/prod/udam-assets/71bd0fbb-2494-4f92-b194-610e3a9407bf.png)

为了解决这种上下文膨胀，我们引入了两个互补的优化机制：

- **CLI 工具解析**：不再让模型直接集成 MCP，而是允许模型执行 shell 命令。CLI 在调用时针对网关动态解析并调用所需工具，从而把 Uber MCP 的 schema 从会话上下文中去除。来自内部 MCP 网关的全部 1,000 多个 MCP 工具都被投射为 CLI 命令。
- **工具搜索**：允许模型搜索工具目录并按需只加载所需工具，可扩展到数千个工具。这种方式缓解了上下文膨胀，通常能减少工具定义占用的 token，并且在可用工具库扩大的情况下仍保持较高的选择准确率，避免大型工具集带来的退化。

### Code-Mode

当工具以 shell 命令的形式直接调用函数时，模型可以在单个脚本中批量执行多个动作。这种批处理对「话多」的工具协议尤其有利。在标准 MCP 工作流下，每个动作都需要单独一轮模型调用：发出请求、把原始响应装入上下文窗口、再依次处理结果。例如执行一条 SQL 查询，需要提交请求、轮询状态 2 到 5 次、再取回输出。code-mode 把整个流程简化为一个自动化的 Python 循环，把中间轮询挡在模型的活跃上下文之外。如图 8 左侧所示，模型参与轮询循环，每个响应都落入它的上下文；右侧则是循环在子进程中运行，只有摘要被传回。

![图 8：同一次数仓查询的两种执行方式](https://tb-static.uber.com/prod/udam-assets/318b7f2c-38d6-415f-aeb3-1859f965c573.png)

我们在同一个会话中，用两条路径各运行 5 条相同的 SQL 查询来做测量：

| 查询 | LLM 工具调用 | Code-mode | 节省 |
| --- | --- | --- | --- |
| SELECT 1（1 行） | 903 | 402 | 55% |
| COUNT(*)（1 行） | 954 | 403 | 58% |
| GROUP BY LIMIT 20（20 行） | 1,600 | 457 | 71% |
| SHOW COLUMNS（175 行） | 2,200 | 900 | 59% |
| SELECT * 宽表（50 行） | 1,431,594 | 900 | ~100% |

*同一 Claude Code 会话中测得的每次查询 token 数。*

前三行凸显了主要发现：即使结果集极小、远低于响应大小限制，code-mode 也能把 token 用量减少 **50% 以上**。这些节省并非来自绕过大数据负载，而是来自消除不必要的开销，包括 schema 初始化、多轮轮询和冗余的逐步推理。

批量工作流会进一步放大这一效应：原本需要 N 轮模型调用的循环变成一个脚本，节省可累积**超过 90%**。通过为访问最频繁的 MCP 服务器部署 **25 个以上**预构建的 code-mode 技能，我们确保标准工作流默认走最具成本效益的路径。

### SaaS MCP

管理第三方软件比管理内部服务器难得多。供应商把 MCP 服务器设计成暴露完整产品能力，因为他们无法预判具体客户的使用方式。例如，某办公套件把 **49 个工具**打包进单个服务器，需要约 **2.2 万 token** 的 schema；即时通讯与项目跟踪类供应商则分别提供 **34 个**和 **46 个**工具。只要加载两三个供应商服务器，用户还没输入 prompt，智能体背负的 schema 开销就已超过它正在编辑的文件。

为解决这一问题，我们让 SaaS MCP 服务器经由我们的 MCP 网关路由，机制与内部 MCP 相同。我们还把这些 MCP 全部暴露为任何智能体界面都可调用的 CLI。此外，我们在 code-mode 插件中为每个服务器编写专用技能，把常见工作流封装起来。这让我们在众多 SaaS 供应商上解锁了高效的智能体工作流。

![图 9：每个 SaaS MCP 服务器都暴露在 MCP 网关之后，以保证统一、高效的访问模式](https://tb-static.uber.com/prod/udam-assets/869a5712-36fb-402b-ad9e-71ae6a6105cf.png)

## 优化请求 / 轮次

缺少上下文支撑的智能体会「慢速失败」而不是「便宜地失败」：它会反复发送不断膨胀的上下文窗口，只为再多搜一个地方。预先提供更丰富的信息，仍然是降低这类搜索开销最有力的单一杠杆。

### 上下文工程

在 Uber 庞大的代码库和数据生态中——数亿行代码、数千张表——智能体的大部分轮次花在定位信息而非生成代码上。为此，我们构建了 **AI Context Graph**：一个包含 **2,400 万节点、8,000 万边**的统一网络，覆盖 **86 种节点类型和 117 种边类型**。它整合了来自 **30 多个内部系统**的数据，包括服务、工程团队、事故日志、pull request、架构设计文档、部署、数据集以及历史表使用查询，并允许任何智能体用自然语言查询。

![图 10：同一条 prompt 提交给同一模型时，有图支撑与无图支撑的执行路径对比](https://tb-static.uber.com/prod/udam-assets/1c6c7371-a4e4-47dd-9496-315bea2bf102.png)

有图支撑的智能体查询了历史使用情况，找到 50 多位分析师使用的特定表，并在 **38 秒**内给出答案。相反，没有图支撑的智能体看不到那张表：它花了 **20 分钟**检查服务代码、启动了 2 个子智能体、遭遇 3 次错误，最后错误地得出该数据集无法查询的结论。

### 可见性与教育

这一组杠杆是可见性与反馈闭环，帮助工程师和智能体更快收敛。

**状态栏。** 我们在 harness 状态栏中放入了实时成本计数器，按每个 harness 以及每位用户的所有 harness 追踪实时支出。

![图 11：状态栏，以及随附发布的会话分析器与效率指南](https://tb-static.uber.com/prod/udam-assets/e0878e4d-55b4-4620-bb9f-cfc99771856c.png)

**可见性与支出层级。** 为避免设置严格的硬性上限，我们实施了实时支出追踪和自动提醒：

- 状态栏实时计数器：会话运行成本始终在终端可见。
- Harness 池：所有交互式 harness 共享同一层级，而非按工具分别设预算；托管智能体则单独分层。
- Slack 提醒：在预期支出的 50%/80%/100% 时告警，让工程师有时间做规划。
- 便捷审批流：层级升级由经理签核，并快速生效。
- 成本检查技能与提示：一个仪表盘技能，按需提供成本明细，并在状态栏中做实时指导。

这些机制让工程师能够独立评估任务 ROI，同时抑制费用失控。

**会话分析仪表盘。** 状态栏能显示会话的总支出，但看不到成本驱动因素，也给不出可执行的效率步骤。通用指南提供高层原则，却无法评估单个开发者的工作流。会话分析仪表盘通过直接检查会话产物来弥补这一缺口。

它直接内建于运行时，零配置、无需主动开启。执行 **cost dashboard** 技能会分析该用户在其使用的所有 harness、本地与远程云沙箱中的全部会话 trace。它不产出汇总指标，而是跨会话标记 **16 类**不同的反模式，并为每一类配上财务影响和针对性补救措施。部分类别包括：

- **模型路由欠优**：本可由 Sonnet 轻松完成的简单多轮会话却跑在 Opus 上。
- **上下文窗口膨胀**：大型 MCP 负载（例如 40KB 的响应）滞留在上下文中，导致后续轮次重复计费。
- **缓存过期低效**：长时间中断后恢复会话，过期的 prompt 缓存迫使全价重建前缀。
- **prompt 初始化开销**：在任何用户输入之前就预载了 10 万 token 的系统指令与工具定义。

## 下一步？

正在推进的工作包括：

- **扩大托管智能体队伍**：对每个新智能体，我们都遵循一致路线图：确定目标产出指标、搭建评估基准、找出帕累托最优模型。这一系统化方法旨在把 SDLC 的每个阶段推向工厂成熟度模型的更高层级。
- **动态模型路由**：我们正在扩展基准，覆盖更多编程语言、代码仓库和智能体形态。鉴于模型能力差异巨大，有效的模型路由高度依赖全面的评估。
- **深化 context graph 集成**：我们正在向更广泛的自主智能体开放图查询能力。
- **把会话分析演进为实时开发者指导**：从周期性的批量反模式检测转向持续的 trace 监控，把个性化、实时的效率建议直接交付给工程师。
- **持续的技能改进**：我们正在研究一种自动化方式，记录智能体技能执行中的 papercut，并从收集到的 trace 自动生成技能更新。

## 结论

管理并遏制不断上涨的 AI 编程开支，同样是一个可解的工程问题。通过消除浪费性的零价值 token 消耗，而不是仅仅依赖更低的单价或降级工具，我们在使用量扩大 7 倍的同时，降低了所有指标上的单位成本，并提升/保持了输出质量。

核心的战略转变是从交互式开发者工作流转向完全托管的智能体。把 SDLC 工作负载迁入托管环境，就能完全掌控模型路由、执行 harness 和运营支出。优化一支专门的托管智能体队伍——每个都配有专属评估基准和帕累托高效的模型——本质上比在数千名工程师的各个终端会话上逐一优化更省成本、更可扩展。
