## 与 AI 研发效能的相关性

**高度相关。** 这篇文章给出了一个可以直接搬用的分析框架：把智能体总开支拆成「用户数 × 人均请求 × 每请求输入 token × 每请求输出 token × 每 token 价格」，再逐项找杠杆。Uber 的结论是，与其只等模型降价，不如消灭零价值的 token 消耗；他们在使用量扩大 7 倍的同时，把每千次请求成本和每次会话成本都压了下来。对研发效能团队而言，文中的度量口径、托管智能体的「按交付计价」方式，以及把交互式会话迁到托管智能体的判断，都比单纯的工具选型更有参考价值。文中降幅来自 Uber 内部环境，换到其他组织必须重新测量。

## 引言

AI 工具已经嵌入 Uber 软件开发的每个阶段。超过 **70% 的 pull request** 由本地或云端智能体完成；工程师在软件开发生命周期（SDLC）中积累了 **3,600 多个 agent skill**，每天执行 **3 万次以上**。

Uber 在 AI Engineer 2026 大会上分享了软件工厂的愿景，以及围绕生命周期构建的构件和托管智能体。随着这条路线推进，越来越多的会话不再由人发起，而是由自动化托管智能体处理：代码审查、CI 失败自愈、带视觉验证的端到端 PR、值班告警分诊、缺陷调试，以及各类代码维护任务——人只负责评审和升级。

如图 1 所示，2026 年 2 月到 8 月，全体员工的各类智能体产品周活跃用户增长 **7 倍**，每周智能体请求量增长 **9.4 倍**；同期 AI 总支出从 4 月起基本稳定，原因是各方面都在做优化。

![图 1｜2026 年 2 月至 8 月中：周活跃用户、智能体请求量与成本（用户跨工具去重）](https://tb-static.uber.com/prod/udam-assets/dda106d3-0439-427b-b780-c399dc85c7c8.png)

由于采用程度、工作负载结构和模型升级都在持续变化，要单独看出自身优化的效果，必须固定一个模型来观察，因为模型家族每次升级都会改变行为。Uber 在 2 月至 7 月固定模型做了对比：每千次模型请求的成本较峰值下降近 **34%**，每次会话成本较 6 月峰值下降 **52%**。

![图 2｜固定模型下的成本优化效果；每次会话成本的数据从 5 月底开始](https://tb-static.uber.com/prod/udam-assets/b25d175f-821b-4ba6-a149-14e5c95a25cb.png)

文章的结构是：智能体会话运行的四个层次、用来拆解支出的成本公式、每一项怎么度量，以及如何在每一层做优化。

需要说明口径：文中所有价格和供应商指标都基于公开信息，成本效率提升来自在标准分层定价内更智能地路由 Uber 内部工作负载。具体的降幅是 Uber 环境特有的，取决于代码库、团队规模和智能体工作流；但「用真实工作做基准，同时优化准确率和成本」这套方法是可以通用的。

## 软件工厂及其成本公式

### 智能体使用的四个层次

Uber 按专用到通用的顺序把 AI 使用分成四层。层次越高，对成本、质量和模型选择的控制力越强。

![图 3｜智能体会话运行的四个层次](https://tb-static.uber.com/prod/udam-assets/6f6a2f9d-8e70-45a8-9637-9ffa118aa23b.png)

### 成本公式

在任何一层，一次智能体会话的成本都可以拆成下面六项，并且可以分别度量和优化。

![图 4｜总开支拆成六个相乘的项](https://tb-static.uber.com/prod/udam-assets/caf91e7d-085d-4014-918f-afef7f7b299b.png)

前两项代表采用与参与度（用户数、人均请求数），这是希望持续增长的。中间三项才是优化空间：智能体在工程师实际请求之外、为自己完成的工作。Uber 的主要精力放在这里，包括让智能体更快规划、减少多余轮次和错误、优化输入 token 等机制。最后一项是每 token 的价格。

## 如何度量

Uber 每周和每月追踪下面几组指标，用于短期和长期预测与规划：

| 层次 | 指标 | 回答什么问题 |
| --- | --- | --- |
| 组合层 | 归属总成本、归属用户数、各工具/智能体的成本、用户与支出占比 | 钱花在哪里，哪个工具带来了变化 |
| 单工具的单位经济性 | 每用户成本、每用户请求数、每千次请求成本、每请求的输入/输出/总 token、每百万 token 成本、每千次会话成本、每活跃会话小时成本、prompt cache 命中率 | 工具是真的变便宜了，还是只是用量转移了 |
| 模型经济性 | 每个模型的成本与成本占比、请求与请求占比、每千次请求成本、每百万 token 成本 | 哪些模型发布真正改变了账单，以及是在相同还是不同的单价下 |
| 驱动因素拆解 | 把成本变化依次拆成采用（用户数）、参与（人均请求）、输入负载（每请求输入 token）、输出负载（每请求输出 token） | 数字为什么变，且不留下无法解释的残差 |
| 托管智能体产出 | 按产出计价（每个已合并 PR、每次审查、每条告警、每次清理的成本）、质量信号（回滚率、F1、MTTR）、吞吐量（落地的 diff、发出的审查、分诊的告警） | 每个托管智能体每单位价值是否更便宜，模型迁移后质量是否守得住 |

## 优化杠杆

下面几节展开成本公式中每一项的优化手段。有些手段会同时影响一行或多行。

| 影响项 | 主要手段 |
| --- | --- |
| 价格 / Token | 基准驱动的帕累托最优模型选择；默认模型设置 |
| Tokens / 请求 | 400K 上下文上限与默认 Medium 推理强度；prompt caching；工具搜索与 CLI 解析的 MCP 调用；code-mode 批量工具调用；网关路由的 SaaS MCP |
| 请求 / 轮次 | 基于图的上下文；持续的 skill 优化；可见性与教育 |
| 可见性与教育 | 状态栏实时成本；可见性与支出层级；会话分析面板 |

## 优化价格 / Token

单价由供应商决定，但选哪个模型跑哪类工作负载由 Uber 决定。在所有托管智能体层，团队都选对该工作负载最「帕累托有效」的模型——这里的含义是每个已完成任务的成本、输出质量和模型可靠性三者综合最优。

### 基准驱动的模型选择

模型选择分四步，对每个托管智能体都一样：

1. 用该智能体的真实工作构建基准。
2. 在同一个接口后面接上任意模型（前沿模型或开放权重模型）的 harness 上运行。
3. 迁移到帕累托最优的那个模型，并持续跟进——前沿每隔几周就变一次。

往后，Uber 还会汇总各托管智能体的洞察，用来测试和部署各种模型路由策略。

以负责所有 PR 的 AI 代码审查工具 **uReview** 为例：基准来自带有已知缺陷的真实 PR，按易、中、难分级，用精确率、召回率、F1 衡量，同时看每次审查成本、延迟、超时和噪声。如图 5，换模型后 F1 提升，同时每个 PR 的成本大幅下降。图中虚线是帕累托前沿，落在其左下方的配置都会被更便宜或更好的方案击败。

![图 5｜uReview 测试过的所有配置](https://tb-static.uber.com/prod/udam-assets/a3b68d79-4d1f-47d5-9524-5c0c404bdbd2.png)

Uber 还用大型单仓中的数千个真实 PR 构建了内部的 **Uber SWE Benchmark**，让前沿模型和开放权重模型跑不同类型的任务，用来指导整个 SDLC 托管智能体的模型选择。

### 默认模型选择

在交互式界面里，token 单价是固定的，但可以在模型之间分配 token。主要由两个默认设置决定：会话的初始模型和子智能体模型。

实践下来，**子智能体默认设置**是影响最大的杠杆，而且越来越重要：随着最新模型能力提升多智能体编排效果，发起子智能体的会话比例持续上升。子智能体做的是输入明确、边界清晰的任务，通常不需要前沿级推理，所以默认用更弱、更便宜的模型，同时允许手动覆盖。主模型负责任务拆解和评估，子智能体负责执行。

## 优化 Tokens / 请求

每一轮都会重新发送完整对话历史、项目上下文和工具结果。任何能减少单次请求负载的做法，都会在整个会话里被反复放大。

### 默认配置

所有交互式 harness 共用一个统一封装来管理安装、配置、认证和成本可见性。两项标准默认配置直接降低了每请求的 token 消耗：

- **在 40 万 token 时自动压缩**，即使模型支持 100 万上下文也一样。这个阈值在模型表现、缓存突发和重复输入成本之间取得平衡；实测全舰队每请求输入 token 明显下降。
- **推理强度默认 Medium**。输出 token（包括内部推理 token）在主模型上的计费倍率高于输入 token，这项调整直接压低了最贵的 token 类别。对很大一类任务，Medium 在成本和质量之间比较平衡。

### Prompt Caching 策略

缓存策略取决于供应商的缓存读写经济学。既然每轮都要重发完整历史，缓存前文就能避免重复付全价：命中缓存后的读取只需标准输入价格的 **0.1 倍**。但写入有溢价：**5 分钟缓存 1.25 倍，1 小时缓存 2 倍**。所以最优 TTL 取决于两轮之间的间隔长短。可选 TTL 包括 Anthropic 的 5 分钟和 1 小时，以及 OpenAI 的 30 分钟。

![图 6｜同样 5 轮对话在两种 TTL 下的成本对比](https://tb-static.uber.com/prod/udam-assets/f6134160-6beb-4272-8d88-2bee792d0403.png)

工程师经常让交互式会话空闲超过 5 分钟，因此 Uber 把默认 5 分钟 TTL 改成 1 小时。此前这些空闲会作废前缀缓存，迫使全价重建上下文。子智能体则保留 5 分钟 TTL，因为它们只做单个、短命的聚焦任务。

### 通过 Shell 执行 MCP 工具

Uber 所有 MCP（Model Context Protocol）交互都经过统一网关。这个入口覆盖内部和第三方 SaaS 的 **1,000 多个 MCP 服务器**，实现集中认证和策略执行。

但标准 MCP 会把所有工具的 schema 直接加载进每个会话，不管这次会不会用到。例如装了 100 多个工具时，预加载会给初始 prompt 增加约 **5 万到 7 万个 token** 的 schema，而且每轮上下文都要重发。

![图 7｜三种接入同样工具的方式下，会话开始时智能体已经背着的负担](https://tb-static.uber.com/prod/udam-assets/71bd0fbb-2494-4f92-b194-610e3a9407bf.png)

为此 Uber 加了两个互补机制：

- **CLI 工具解析**：不让模型直接集成 MCP，而是让它执行 shell 命令；CLI 在调用时向网关动态解析并调用所需工具，session 上下文里不再有 Uber MCP 的 schema。内部 MCP 网关的 1,000 多个工具全部投影为 CLI 命令。
- **工具搜索**：可扩展到数千个工具，模型先搜索工具目录，再按需加载。这样既缓解上下文膨胀、通常减少工具定义占用的 token，又能在工具库扩大时保持较高的选择准确率，避免大工具集带来的退化。

### Code-Mode

当工具以 shell 命令的形式暴露后，模型可以在一个脚本里批量执行多个动作。这对「话多」的工具协议尤其有利：标准 MCP 流程下，每个动作都要单独一轮模型调用——发请求、把原始响应读进上下文、再依次处理。以一次 SQL 查询为例，要提交请求、轮询状态 2 到 5 次、再取回输出。code-mode 把整个流程放进一个自动化 Python 循环，中间轮询不进入模型的活跃上下文。图 8 左侧是模型参与轮询、每个响应都落进上下文；右侧是循环在子进程里跑，只把摘要带回来。

![图 8｜同一次数仓查询的两种执行方式](https://tb-static.uber.com/prod/udam-assets/318b7f2c-38d6-415f-aeb3-1859f965c573.png)

Uber 在同一会话里用两条路径各跑 5 条相同的 SQL 做测量：

| 查询 | LLM 工具调用 | code-mode | 节省 |
| --- | --- | --- | --- |
| SELECT 1（1 行） | 903 | 402 | 55% |
| COUNT(*)（1 行） | 954 | 403 | 58% |
| GROUP BY LIMIT 20（20 行） | 1,600 | 457 | 71% |
| SHOW COLUMNS（175 行） | 2,200 | 900 | 59% |
| SELECT * 宽表（50 行） | 1,431,594 | 900 | 约 100% |

前三行说明了主要结论：即使结果集很小、远低于响应大小限制，code-mode 也能把 token 用量降一半以上。省下来的不是大数据负载，而是 schema 初始化、多轮轮询和逐步推理这些多余开销。批量工作流会进一步放大效果：原本需要 N 轮模型调用的循环变成一个脚本，节省可以超过 90%。Uber 为最常用的 MCP 服务器预置了 **25 个以上 code-mode skill**，让标准工作流默认走最省钱的路径。

### SaaS MCP

第三方软件比内部服务器难管得多。供应商不知道客户的具体用法，所以倾向于把完整产品能力暴露出来：某办公套件把 **49 个工具**打包进一个服务器，schema 约 **2.2 万 token**；即时通讯和项目跟踪类供应商分别提供 34 个和 46 个工具。只要加载两三个供应商服务器，用户还没输入内容，智能体背的 schema 开销就超过了正在编辑的文件。

因此 Uber 让 SaaS MCP 服务器也经过自己的 MCP 网关，机制与内部 MCP 相同；同时把这些 MCP 全部暴露为任何智能体界面都能调用的 CLI。此外，在 code-mode 插件里为每个服务器编写专用 skill，把常见工作流封装起来。这样才在众多 SaaS 供应商上跑通了高效的智能体工作流。

![图 9｜所有 SaaS MCP 服务器都放在 MCP 网关后面，保证统一、高效的访问方式](https://tb-static.uber.com/prod/udam-assets/869a5712-36fb-402b-ad9e-71ae6a6105cf.png)

## 优化请求 / 轮次

没有上下文支撑的智能体会慢速失败而不是便宜地失败：它会不断把越来越大的上下文再发一遍，只为多搜一个地方。提前提供更丰富的信息，仍然是减少这类搜索开销最有力的杠杆。

### 上下文工程

Uber 的代码库和数据生态有数亿行代码和数千张表，智能体大多数轮次都花在找信息，而不是写代码。为此他们构建了 **AI Context Graph**：一个包含 **2,400 万个节点、8,000 万条边**的统一网络，覆盖 **86 种节点类型和 117 种边类型**，整合了 30 多个内部系统的数据——服务、工程团队、事故日志、PR、架构设计文档、部署、数据集和历史表使用查询——任何智能体都能用自然语言查询它。

![图 10｜同一条 prompt、同一个模型，有图支撑和没有图支撑的执行路径对比](https://tb-static.uber.com/prod/udam-assets/1c6c7371-a4e4-47dd-9496-315bea2bf102.png)

一个有图支撑的智能体查询了历史使用情况，找到 50 多位分析师用过的那张表，**38 秒**给出答案。没有图支撑的智能体看不到这张表，花了 **20 分钟**翻服务代码、启动 2 个子智能体、撞上 3 个错误，最后还错误地判断数据集不可查询。

### 可见性与教育

这一组杠杆是可见性和反馈闭环，帮助工程师和智能体更快收敛。

**状态栏。** harness 状态栏里有实时成本计数器，按每个 harness 和该用户所有 harness 汇总显示当前花费。

![图 11｜状态栏，以及随附的会话分析器和效率指南](https://tb-static.uber.com/prod/udam-assets/e0878e4d-55b4-4620-bb9f-cfc99771856c.png)

**可见性与支出层级。** Uber 没有设硬性上限，而是做实时花费追踪和自动提醒：

- 状态栏实时计数器：会话成本始终在终端可见。
- Harness 池：所有交互式 harness 共用一个层级，而不是按工具分别设预算；托管智能体单独分层。
- Slack 提醒：在预期支出的 50%、80%、100% 时告警，给工程师留出规划时间。
- 便捷的审批流：经理批准升级层级，并快速生效。
- 成本检查 skill 与提示：一个仪表盘 skill，按需给出成本明细，并在状态栏里做实时指导。

这些让工程师能自行评估任务 ROI，同时避免费用失控。

**会话分析面板。** 状态栏只能看到会话总花费，看不到成本驱动因素，也给不出可执行的建议；通用指南只有高层原则，无法评估个人的具体工作流。会话分析面板直接检查会话产物来补这个缺口。它内置于运行时，零配置、无需主动开启。运行 `cost dashboard` skill 会分析该用户在所有 harness、本地和远程云沙箱里的全部会话 trace，不产出笼统指标，而是标出 16 类反模式，并为每一类给出财务影响和针对性补救。类别包括：

- **模型路由不当**：本可以用 Sonnet 完成的简单多轮会话却跑在 Opus 上。
- **上下文窗口膨胀**：大块 MCP 负载（例如 40KB 响应）留在上下文里，后续每轮都要重复计费。
- **缓存过期浪费**：长时间中断后恢复会话，缓存已过期，被迫全价重建前缀。
- **prompt 初始化开销**：用户还没输入，就先加载了 10 万 token 的系统指令和工具定义。

## 下一步

正在推进的工作包括：

- **扩大托管智能体队伍**：每个新智能体都按同一路线推进——确定目标产出指标、搭建评估基准、选出帕累托最优模型，从而把 SDLC 的每个阶段往工厂成熟度模型的上层推。
- **动态模型路由**：扩展基准，覆盖更多编程语言、代码仓库和智能体形态。模型能力差异很大，有效的路由高度依赖充分评估。
- **加深 context graph 集成**：让更多自主智能体用上图查询能力。
- **把会话分析变成实时开发指导**：从定期批量检测反模式，转向持续监控 trace，把个性化的实时效率建议直接推给工程师。
- **持续改进 skill**：自动记录 skill 执行中的 papercut，并从收集到的 trace 自动生成 skill 更新。

## 结论

控制和压降不断上涨的 AI 编程费用，是一个可解的工程问题。Uber 的做法不是只靠更低的单价或降级工具，而是消灭浪费掉的零价值 token 消耗；结果是使用量扩大 7 倍的同时，所有指标上的单位成本都在下降，输出质量还得到提升或保持。

核心战略转变是从交互式开发者工作流，转向完全托管的智能体。把 SDLC 工作负载迁到托管环境，就能完全控制模型路由、执行 harness 和运营支出。优化一支专门的托管智能体队伍——每个都配有专属评估基准和帕累托最优模型——本质上比在数千名工程师的终端会话上逐个优化更省钱、更可扩展。
